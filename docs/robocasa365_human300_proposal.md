# DiT4DiT human300 训练方案（已批准10k）

状态：用户已批准先训10k并开启goal。数据下载、解压、全任务数据验收及 Cosmos 官方权重哈希核验已完成；单卡 checkpoint 保存、恢复及采样预检通过，正式训练正在运行。当前采用1张 A100、microbatch=1、梯度累积64，global batch=64。训练尚未完成，最终验证和闭环评估仍待执行。

## 目标与比较范围

在现有 RoboCasa365 PandaOmron 接口上，以官方 `pretrain_human300` 为数据范围训练 DiT4DiT。对齐 π0.5 的 human300 数据条件、目标环境和评估口径；不声称直接复现 π0.5 的优化器、模型预训练或效果。π0.5 原始训练配置尚待核对，以下超参数是 DiT4DiT 的拟定方案。

主结果报告 human300-only 在 target 50 任务上的迁移表现。若所参照的 π0.5 实验还有 target 微调，则另设第二阶段、单独记录 target 示范数量和更新步数，不能与 human300-only 混报。

## 数据

采用已固化的官方 300 任务清单：约 30,000 条人类示范，482 小时，以下载后的 metadata 实测为准。全部下载的 target 数据不加入 human300 预训练。镜像中多出的 PlaceOnDishRack 不进入该训练清单；4 个 atomic/composite 目录分类差异需核验任务 metadata。

先按官方 LeRobot 加载函数的 `100_demos` 规则选择：保持 episodes.jsonl 顺序，以 filter_key_seed=0 打乱取100条。此处核对的是官方加载器默认值，不声称已核实 π0.5 私有运行的随机种子。再按任务、按完整 episode 固定 95/5 训练/验证划分，每任务95/5条，共28,500/1,500条，划分 seed=42。同一 episode 的窗口不得跨集合。只在训练轨迹上计算共享归一化；使用有界内存统计流程。明确该开发设置使用约 95% human300 示范；若最终要求与使用全部示范的基线严格对齐，冻结超参数后需重新训练全数据版本，不能把开发运行标成全量训练。

复用三相机、16 维原始 state、12 维动作、32/64 容器和 padding mask。保留完整底盘、控制模式与夹爪；不筛成固定底盘子集。action horizon=16，视频/动作时间对齐沿用并核验现有适配器。正式输入拟定每路 224×224，三路拼图；未来视频采样保持既有 2:1 时序配置，通过 metadata 与实际样本确认。

## 初始化与训练

主实验：可验证的 Cosmos-Predict2.5-2B 视频、文本及 VAE 权重 + 随机初始化 Action DiT（含 state encoder）。GR1 完整策略只用于独立接口对照，不作为主实验初始策略。Cosmos 已按固定提交的官方 Diffusers 转换代码完成转换；视频、VAE、全部4个文本分片和 tokenizer 均与 NVIDIA 官方文件哈希一致。配置 JSON 因序列化版本不同不宣称逐字节相同。

按用户后续授权，使用可用的1、2或4张独占 A100 80GB，不抢占其他作业。global batch=64，microbatch=1，每卡梯度累积为64/卡数。当前单卡完整视频与动作联合训练已通过显存验收：可训练主权重为FP32，前向使用框架混合精度，视频启用梯度检查点。恢复训练要求配置和源码身份一致；现有多卡扩容辅助函数仅校验迁移方案，尚未接入实际跨卡数恢复，不能直接改变卡数续训。batch16只是待确认建议，未应用。

| 项目 | 拟定值 |
| --- | --- |
| 主训练预算 | 10,000 optimizer steps |
| 更新模块 | 视频 DiT + 完整 Action DiT |
| 冻结模块 | 文本编码器、VAE |
| 动作学习率 | 1e-4 |
| 视频学习率 | 1e-5 |
| 优化器 | AdamW，betas=(0.9,0.95)，eps=1e-8，weight_decay=1e-8 |
| 调度 | warmup 500 steps，之后 cosine，结束为各组峰值的 0.1 |
| 梯度裁剪 | 1.0 |
| 目标 | action flow matching + video flow matching，初始权重1:1 |
| checkpoint | 每2,000步保存可恢复状态，2k/4k/6k/8k/10k保留快照 |

保留公开代码的梯度语义：动作 loss 更新动作分支，视频 loss 更新视频分支，不能声称 action loss 通过 detach 更新视频骨干。记录每个参数组的真实梯度、权重变化与损失量级。

10k×64=64万次窗口抽样；不是64万独立示范，也不是无重复epoch。完整训练需要在短程计时后给出总 GPU 小时和存储预算。耗时估算为剩余步数×实测每步秒数，另计验证、checkpoint和闭环评估；目前不给未经测量的天数承诺。

## 执行顺序及验收

1. 下载、SHA256校验、解压和全任务 schema/episode/视频审计；补齐环境和权重，生成不可变manifest。
2. 用户确认后进行100–200步有界运行：真实forward/backward、双分支非零梯度、显存/吞吐、动作反归一化和checkpoint恢复。预检输出与正式训练隔离。
3. 若预检通过，从声明的初始化和seed开始正式10k调度；2k与10k为检查关卡，若出现NaN、分支未更新、数据错误或保存恢复失败则停下修复。
4. 每1k固定验证窗口检查FM loss；同时固定推理噪声，报告真实采样动作的平移/旋转/底盘误差、mode/夹爪准确率，分别观察chunk首、中、末端。不用FM loss代替策略表现。
5. 2k/6k/10k时在预先固定的开发场景做闭环评估；最终checkpoint在独立最终种子上评估target 50任务，每任务50次，共2,500条rollout。报告atomic/composite、seen/unseen与总体按任务宏平均成功率及置信区间。官方环境协议与诊断修改协议分别标注；模型独立控制全部动作。

最终50任务评估必须与π0.5参考的任务集、horizon、场景、种子规则、执行chunk长度和环境版本对齐后，才能声称可比。模型选择用开发种子，最终种子不参与选择。第二个训练seed和target微调属于后续可选预算，不默认启动。
